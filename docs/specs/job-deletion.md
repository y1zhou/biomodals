# Job deletion

Status: Product interview complete; implementation authorized and in progress on `feat/job-deletion` in both repositories.

Researched 2026-09-24 against backend `main` at `6052536465844a1c1166f0100abc89ca436b5f3a` and the adjacent frontend checkout. Source links below refer to those checkouts; line numbers can move after implementation. This is the consolidated design record for both repositories.

## Confirmed scope

The research brief requests owner-initiated Job soft deletion in SQLite and removal of locally cached files under the BioModals work directory. This is design research only. It does not authorize implementation, production deletion, remote cleanup, deployment, or a restore/trash feature.

The meaning of “work directory” needs precision: the service defaults to `.biomodals/state` and `.biomodals/cache`, configured independently with `BIOMODALS_STATE_DIR` and `BIOMODALS_CACHE_DIR`. Production deliberately places these outside the checkout at `/var/lib/biomodals/production/state` and `/var/cache/biomodals/production`. An implementation must target configured service stores rather than recursively delete a checkout or assume one common parent. Sources: [config.py:268](../../src/biomodals/service/config.py#L268), [production service:10](../../deploy/biomodals-api.service#L10).

### Accepted product decisions

- Deletion is owner-initiated and limited to terminal Jobs: `succeeded`, `partial`, `failed`, and `cancelled`. Active or unresolved Jobs must finish or be cancelled first. The existing active-state definition includes `queued`, `running`, `finalizing`, `cancel_requested`, `state_unknown`, and `blocked`; these are not eligible. Source: [store.py:65](../../src/biomodals/service/store.py#L65).
- Remove normal website access and the Job's locally cached results and retained inputs. Keep Modal outputs, remote execution records/logs, shared scientific caches, and historical billing unchanged. This is not complete data erasure.
- Deletion is permanent from the owner's perspective, with no Trash or Restore feature. Preserve the internal database identity and submission key; old links become unavailable and old submission replay cannot create replacement computation or resurrect the deleted Job.
- Allow deleting source Jobs independently of their existing extension/clustering children. Keep children usable, forbid new source-based operations from deleted sources, and preserve recovery of already-admitted children.
- Hide the Job immediately and block new access. Existing downloads may finish. Local cleanup is eventual, retries failures, and resumes after API restart; acceptance does not claim every byte is already reclaimed.
- Show a red Delete button only on eligible Job detail pages, next to Refresh, with a confirmation popup. Do not add deletion to My Jobs or introduce bulk deletion.
- Normal administrator Job/log endpoints also hide deleted Jobs. Retained database metadata remains for internal operational/audit purposes only; no administrator trash browser or new metadata-scrubbing feature.
- No live cross-tab synchronization initially. Another already-open tab may display previously loaded information until refresh/navigation or a subsequent server request reveals unavailability. All new server access is blocked immediately.

Technical details to finalize in the implementation plan include repeated-delete and deleted-submission response codes, safe source-link presentation, cleanup diagnostics, and treatment of already-open log streams consistent with the accepted in-flight-download policy. None should restore owner access or expand this feature into remote erasure.

## Existing persistence and API boundaries

`ServiceStore` owns one SQLite database, currently schema version 9. The `jobs` table has no deletion field, retains immutable identity and result metadata, enforces `(owner_user_id, tool, idempotency_key)` uniqueness, makes `pending_validation_id` unique, and has a self-reference for `source_job_id`. `JobState` is lifecycle state, so a separate tombstone is a smaller conceptual change than adding a fake scientific state called `deleted`. The latter is a proposal, not a chosen schema. Sources: [store.py:87](../../src/biomodals/service/store.py#L87), [store.py:98](../../src/biomodals/service/store.py#L98), [store.py:214](../../src/biomodals/service/store.py#L214).

There is no Job DELETE route. Shared endpoints use owner lookup before detail, refresh, cancellation, retry, preparation, and download; each tool also has owner-gated input/result routes. New deletion should use the established authenticated unsafe-request dependency for CSRF protection and enforce ownership in the state-changing transaction. Checking ownership only before an asynchronous operation leaves a race with later mutations. Sources: [jobs_api.py:84](../../src/biomodals/service/jobs_api.py#L84), [jobs_api.py:226](../../src/biomodals/service/jobs_api.py#L226), [http_contract.py:224](../../src/biomodals/service/http_contract.py#L224), [alphafold3/router.py:148](../../src/biomodals/service/alphafold3/router.py#L148), [gromacs/router.py:131](../../src/biomodals/service/gromacs/router.py#L131), [humanization/router.py:113](../../src/biomodals/service/humanization/router.py#L113), [nanobody_humanization/router.py:117](../../src/biomodals/service/nanobody_humanization/router.py#L117).

Filtering only Job history is insufficient. The following query families need explicit policy; applying a universal `deleted_at IS NULL` mechanically would also remove safety evidence needed internally.

## Races that determine implementation size

`JobLifecycle.advance`, cancellation, administrator state resolution, and retry use a shared per-Job `asyncio.Lock`. Staging uploads request/launch metadata, deletes local pending input, clears validation references, and launches the remote root while holding this lock. Deleting pending inputs outside that coordination can break staging. Existing cancellation only accepts queued/running/cancel-requested states; queued Jobs without a root become cancelled locally, while other cancellation is delivered later by reconciliation. “Allow deletion in every state by calling cancel” therefore does not follow from the current implementation. Sources: [tool_runtime.py:124](../../src/biomodals/service/tool_runtime.py#L124), [tool_runtime.py:139](../../src/biomodals/service/tool_runtime.py#L139), [tool_runtime.py:326](../../src/biomodals/service/tool_runtime.py#L326), [store.py:1898](../../src/biomodals/service/store.py#L1898).

Result restoration is separate: `restore_result` deduplicates into `_restore_tasks`, shields work from request cancellation, and `_restore_result` does not acquire the lifecycle lock. It can rebuild/publish an archive and restore `cache_cleared_at` after a request that started before deletion. Terminal-only eligibility does not remove this race because completed Jobs can be rebuilding missing results. Cancelling a browser request alone does not stop the shielded task or necessarily stop thread-based I/O. Sources: [tool_runtime.py:524](../../src/biomodals/service/tool_runtime.py#L524), [tool_runtime.py:540](../../src/biomodals/service/tool_runtime.py#L540), [artifacts.py:26](../../src/biomodals/service/artifacts.py#L26).

New downloads/previews perform an owner lookup before awaiting cache acquisition. A deletion can occur between those steps unless admission to new leases is coordinated or visibility is rechecked at the appropriate boundary. An existing `ArtifactLease` holds an open descriptor and protects the archive from ordinary cleanup. `discard` raises on active leases; `clear` skips them. Even if a path is unlinked, that is not proof an open reader has stopped consuming bytes or that physical disk space has already been reclaimed. Sources: [jobs_api.py:200](../../src/biomodals/service/jobs_api.py#L200), [artifacts.py:90](../../src/biomodals/service/artifacts.py#L90), [artifacts.py:364](../../src/biomodals/service/artifacts.py#L364), [test_artifact_cache.py:286](../../tests/service/test_artifact_cache.py#L286).

Archive publication verifies bytes and then atomically replaces the result path under the cache's own thread lock. That lock currently knows nothing about SQLite deletion intent. A filesystem remove followed by a tombstone, or a tombstone followed by a one-off remove without producer coordination, can leave resurrected cache files. SQLite mutations such as `complete_job`, `restore_result_cached`, and retry/state changes also currently update by UUID without a tombstone predicate. Sources: [artifacts.py:377](../../src/biomodals/service/artifacts.py#L377), [store.py:542](../../src/biomodals/service/store.py#L542), [store.py:1868](../../src/biomodals/service/store.py#L1868), [store.py:2068](../../src/biomodals/service/store.py#L2068).

The durable record and filesystem cannot be updated atomically through the existing SQLite transaction. A proposed small design is a tombstone plus durable cleanup-pending/completion information on the same Job row, with idempotent cleanup retried after restart. Reuse the existing lifecycle/cache machinery where feasible. The exact fields, response status, retry scheduling, treatment of busy leases, and producer fencing are unresolved design choices. A durable tombstone must not be cleared by cache reconciliation or ordinary lifecycle mutation. Sources for the available mechanisms: [store.py:2171](../../src/biomodals/service/store.py#L2171), [api.py:98](../../src/biomodals/service/api.py#L98), [tool_runtime.py:599](../../src/biomodals/service/tool_runtime.py#L599).

The documented deployment uses one API worker. Process-local locks are meaningful in that architecture; supporting multiple API workers would require a separate coordination design rather than claiming these locks solve cross-process races. Source: [api-service-architecture.md:635](../research/api-service-architecture.md#L635).

## Lineage and shared assets

Each admitted GROMACS child stores its own serialized request under its own UUID. A clustering request references its remote source and records that source in `jobs.source_job_id`. Continuation also constructs a new request from inspected source information, but `admit` only assigns `source_job_id` for `ClusteringExecutionRequest`; continuation lineage is not completely represented by that SQL column. A future “has children” deletion rule therefore cannot rely on that column alone without addressing continuation lineage. Sources: [gromacs/router.py:137](../../src/biomodals/service/gromacs/router.py#L137), [gromacs/router.py:171](../../src/biomodals/service/gromacs/router.py#L171), [gromacs/router.py:369](../../src/biomodals/service/gromacs/router.py#L369), [gromacs/router.py:514](../../src/biomodals/service/gromacs/router.py#L514).

Deleting a parent's local request/archive does not target the child's independently named local request/archive. That does not prove remote source artifacts are dispensable: child requests are constructed from remote source inspection, and clustering intentionally avoids duplicating the simulation trajectory in its result archive. Preserving remote assets makes local-only deletion a much narrower operation than remote erasure, but a surviving child still needs a deliberate UI behavior for its deleted source link. Sources: [gromacs/modal.py:83](../../src/biomodals/service/gromacs/modal.py#L83), [jobs.py:88](../../src/biomodals/service/jobs.py#L88), [gromacs-trajectory-clustering.md:10](gromacs-trajectory-clustering.md#L10).

AlphaFold3 identical requests can share remote scientific publications: staging waits for active predecessors and sends incomplete predecessor execution IDs for repair. Tombstoned predecessor rows may still be needed for this operational reasoning even when unavailable in owner history. Remote scientific publication cleanup is not a consequence of deleting `<job UUID>.result`. Sources: [alphafold3/modal.py:112](../../src/biomodals/service/alphafold3/modal.py#L112), [alphafold3/modal.py:233](../../src/biomodals/service/alphafold3/modal.py#L233), [store.py:1422](../../src/biomodals/service/store.py#L1422).

## Accounting and migration

Current “published result” accounting counts rows with `result_size_bytes` and a null `cache_cleared_at`, despite its durable-accounting name. The admin view separately reports filesystem archives/staging/pending/validation usage. Startup reconciliation resets cache-presence markers from existing result files. Deletion should keep the chosen logical result count distinct from actual reclaimed local bytes and should not report hidden-but-still-leased bytes as physically gone. Archive temporary directories are absent from the current `.result`/`.part` size scan. Sources: [store.py:485](../../src/biomodals/service/store.py#L485), [store.py:586](../../src/biomodals/service/store.py#L586), [admin_api.py:463](../../src/biomodals/service/admin_api.py#L463), [artifacts.py:485](../../src/biomodals/service/artifacts.py#L485).

The global Modal costs endpoint does not join the Jobs table. `BillingService` reads Modal workspace billing and aggregates environment/tool tags, with an in-memory five-minute cache. Local Job deletion does not remove past provider charges or change this aggregation. Sources: [admin_api.py:677](../../src/biomodals/service/admin_api.py#L677), [billing.py:47](../../src/biomodals/service/billing.py#L47).

A schema change needs a version increment, fresh-schema columns, `JobRecord`/row decoding, readiness compatibility, and migration tests preserving authentication, identity, foreign keys, and existing Jobs. The current initializer supports fresh v9 or one v8→v9 branch and rejects other versions. A v10 implementation must deliberately chain supported v8→v9→v10 upgrades or state a narrower supported upgrade path; simply adding another `elif` can leave a v8 database at v9 after one initialization. Additional cleanup columns can fit the existing Jobs table, avoiding a new table unless the selected behavior needs it. Sources: [store.py:332](../../src/biomodals/service/store.py#L332), [store.py:422](../../src/biomodals/service/store.py#L422), [store.py:443](../../src/biomodals/service/store.py#L443), [store.py:2197](../../src/biomodals/service/store.py#L2197), [test_job_store.py:64](../../tests/service/test_job_store.py#L64).

## Proposed implementation and verification boundary

### Frontend findings

All four Job-producing Tools share Job detail and My Jobs surfaces, so one owner deletion action can serve all of them. Existing confirmation dialogs and authenticated CSRF-aware mutations are reusable. The immediate antibody sequence analysis tool creates no Job and is outside this feature. Sources: [Job detail](../../../biomodals-frontend/src/pages/JobDetailPage.tsx), [My Jobs](../../../biomodals-frontend/src/pages/JobsPage.tsx), [API client](../../../biomodals-frontend/src/api/client.ts).

Removing only the detail query is insufficient: list rows, logs, and tool-specific result/input queries have different keys. Deletion must prevent late responses from reinserting the removed Job, navigate away from its detail, and refresh relevant history/storage views. Existing 404 handling can show a historical URL as unavailable. Completed detail pages do not currently refetch on focus; instant removal from another already-open tab would be additional scope. Sources: [query keys and state helpers](../../../biomodals-frontend/src/jobs.ts), [Job detail](../../../biomodals-frontend/src/pages/JobDetailPage.tsx), [candidate results](../../../biomodals-frontend/src/components/HumanizationResults.tsx).

An existing continuation recovery gap matters if sources may be deleted independently: its pending-intent form only mounts after a successful source inspection, so a deleted-source 404 would prevent recovering an already admitted child whose response was lost. Clustering already permits pending replay despite source inspection failure. Preserve owner/source-scoped pending intents and exact replay rather than clearing them when deleting a source. Conversely, replay of a deleted child's original submission must not create new computation or resurrect its visibility. Sources: [continuation page](../../../biomodals-frontend/src/pages/GromacsContinuationPage.tsx), [clustering page](../../../biomodals-frontend/src/pages/GromacsClusteringPage.tsx), [AlphaFold3 recovery](../../../biomodals-frontend/src/pages/AlphaFold3SubmissionPage.tsx).

For planning, allow roughly 4–6 focused developer-days across both repositories for a terminal-only, single-Job, local-only implementation with durable cleanup, regression coverage, and integration. The frontend portion is approximately 1–2 days after the API contract stabilizes. These are engineering estimates, not measurements or delivery commitments; active cancellation/deletion, bulk actions, restore/trash, immediate cross-tab revocation, or remote erasure would expand scope. This recommended scope needs an API/SQLite migration and frontend rollout, but no scientific Modal app/workflow changes are expected.

A terminal-only, local-cleanup version is a moderate backend feature spanning store/query policy, a shared owner endpoint, lifecycle/restoration coordination, cache/pending cleanup, startup recovery, and focused tests. It is not just a delete button plus one SQL update. Allowing active/unknown deletion, remote erasure, undo, or automatic child cascades substantially expands the design. A dependable estimate should follow those product decisions and the frontend findings; no effort commitment is implied here.
